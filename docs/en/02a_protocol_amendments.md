# 02a Protocol Amendment Record (all made before the test-set run)

All amendments are based on development-set observations, were made before the freeze and the test-set run, and have their reasons recorded. No further amendments are made after the test set is frozen.

| ID | Date | Amendment | Reason (development-set observation) |
|---|---|---|---|
| A1 | 2026-10-13 | **Refined L2 definition**: primary basis L2 = L1 + no violation of the SpotIt+ mined constraints on the columns referenced by the two queries (denoted L2); "all columns of all tables satisfy them" is reported as a supplementary basis, L2-all. | SpotIt+'s own counterexamples pass 0/144 under L2-all and 61/143 under L2: its constraints apply only to the columns relevant to the query, so L2-all is too strict for every method and cannot distinguish between methods. |
| A2 | 2026-10-13 | **Two ParSEval variants**: (a) `parseval`: the official `disprove`, `set_semantics=True` (consistent with the primary contract C_set), hard wall-clock limit of 10 s per pair; (b) `parseval_l1`: the same generator, but every generated database is handed to the shared certifier, only L1/C_set witnesses are accepted, and it restarts with a new random seed within the 10 s — the same-budget version most favorable to ParSEval. The main comparison uses (b). | The official `disprove` first checks the empty database and stops on that basis; an empty-database witness does not satisfy L1 (referenced tables non-empty). Leaving its generator unchanged and only replacing the acceptance condition is the fairest option. |
| A3 | 2026-10-13 | **CGX and all in-house baselines uniformly use "certifier-in-the-loop" acceptance**: in the search phase, only databases that the shared certifier judges to pass L1/C_set are returned; at the end they are still independently recertified on a fresh connection. | Ensures that what each method "finds" is consistent with the protocol endpoint, and avoids unfairness caused by different acceptance conditions. |
| A4 | 2026-10-13 | **Two bases for SpotIt**: author-reported (the incorrect cases in its repository `VeriEQL_results_val_cc_null` that the authors verified and cross-checked) is the main comparison target; recheck by this certifier (original SQL, original DDL) is supplementary. SpotIt+ has no cross-checked release; for it, author-reported = judged non-equivalent at any bound. | On the development set we found that SpotIt uppercases all string literals and does not model NOT NULL/UNIQUE, so only 190 of 434 self-reported cases can be reproduced under the original semantics. To avoid being accused of "deliberately suppressing the opponent", the main comparison still uses the self-reported count, which is the most favorable to it. |
| A5 | 2026-10-13 | **Budget**: keep 10 s per pair (in development-set v1, 99% of witnesses were found within 0.63 s, the longest in 2.4 s; 10 s is already saturated); ablations run on a stratified random subsample of the test set (1,500 distinct pairs), the main methods and baselines on all test pairs. | Running all 8 configurations in full on a 2-core machine would take about 35 hours or more. |
| A6 | 2026-10-13 | **Pairs with completely identical text** (differing only in whitespace/a trailing semicolon) are directly judged "no witness" for all methods and counted in the denominator. | Identical SQL text gives identical results on any database; this is a reliable short-circuit that is the same for all methods. |
| A7 | 2026-10-13 | **L1f (format-faithful) added and made the primary endpoint**: L1f = L1 + text column values conform to the lexical shapes observed in the official database (source: categorical value samples mined from the official BIRD database and published by the SpotIt+ authors, 123 columns) + text columns whose names indicate a date/time and that have no samples must be ISO style. L2 is changed to add the SpotIt+ constraints (on query-referenced columns) on top of L1f. All methods (including baselines) may use the same format knowledge during generation/acceptance. | Development-set v1 witnesses relied heavily on unrealistic text encodings (e.g. `'1990'` written into a datetime column); such "differences" do not exist in real data. Switching to a stricter primary basis is an amendment in the conservative direction. |
| A8 | 2026-10-13 | **Budget changed to 5 s per distinct pair (the same for all self-run methods)**; in addition, on a random subsample of 1,000 distinct pairs of the test set, CGX and ParSEval-L1 are rerun with a 10 s budget as a budget-sensitivity check. Ablations are also run on this subsample (5 s). | On the development set, 99% of CGX's witnesses are found within 0.63 s; a full run at 10 s on a 2-core machine would take about 27 hours, at 5 s about 14 hours. The budget is the same for every method, so fairness is unaffected; SpotIt/SpotIt+ still use their authors' much larger budgets. |
| A9 | 2026-10-13 | **v4 method changes (based on misses on development-set "known positives")**: controlled growth — fan-out replication on one-to-many joins (COUNT and COUNT DISTINCT, HAVING COUNT thresholds), constructing enough probes for LIMIT/OFFSET windows, literal-cover probes (one probe per equality literal), interpolated values between comparable literals. | On the development-set pairs judged incorrect by EX (known non-equivalent), v3 recall was 94.3%; most of the 60 missed pairs have the structures above. |

## After the freeze (test set already run): post-hoc analyses and exploratory runs — none of these are part of the pre-registration; they are listed separately in the paper

| ID | Date | Content | Reason |
|---|---|---|---|
| P1 | 2026-10-14 | **Post-hoc admissibility tier L1n**: L1f + among the query-referenced columns, any column that is never NULL in the official BIRD database must not be NULL in the witness either (nullability computed directly on the official database provided by the user; 420 of 798 columns are never NULL). **O1f / O1n**: recertify using the full-column format profile of the official database (instead of the 123-column sample published by SpotIt+). | Interim results show that about 43% of CGX witnesses rely on NULLs that never occur in real data; this needs to be quantified honestly. |
| P2 | 2026-10-14 | **Correction of the acceptance condition of the random fuzzing baseline**: the frozen fuzzing baseline returns "the first database on which the results differ", instead of accepting by L1f with the "certifier in the loop" as CGX/ParSEval-L1 do. This is inconsistent with the statement of A3 and disadvantages the fuzzing baseline. Remedy: for the pairs where the frozen version "found a database that did not pass L1f", rerun with the same random seed and the certifier in the loop (L1f). For the "not found" pairs the trajectory is exactly the same, so no rerun is needed. The paper reports the corrected numbers and explains this deviation in the main text. | Fairness: the baseline must not be disadvantaged by an implementation oversight. |
| P3 | 2026-10-14 | **Nullability-aware versions (exploratory)**: CGX-v5 (both generation and acceptance avoid referenced columns that are "never NULL in the official database"), Fuzz-v5 (the same information and L1n acceptance), ParSEval-L1n (the same generator, with L1n added to the acceptance condition). All three use exactly the same nullability knowledge and are run on all 6,456 distinct EX-correct pairs with a 5 s budget. | To answer "does the method's advantage still hold under the L1n basis"; the three have equal information, which avoids giving extra help only to our own method. |
| P3-correction | 2026-10-14 | **P3 cancelled**: the nullability-aware versions are superseded by the data profile admissibility tier R (see document 07) and were not run. | Avoids spending compute twice. |
| Q1 | 2026-10-14 07:10 | **Frozen queue paused between two steps**: while CGX+SC was running, SIGSTOP was sent to the bash process running the queue script. The running CGX+SC was unaffected and ran to completion as usual; after it finished, the queue did not start the next step. The remaining steps (known positives, official ParSEval, ablations, 10 s budget) are resumed later with SIGCONT, and while they run there will be no other heavy tasks on the machine. While CGX+SC was running, only small-scale smoke tests at the lowest priority (nice 19) ran concurrently, with a CPU share of about 1–2%. | To free compute for debugging the tier-R methods on the development set, while ensuring that the wall-clock budgets of the frozen steps are not squeezed by concurrent tasks. |
