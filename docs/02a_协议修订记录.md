# 02a 协议修订记录（全部发生在测试集运行之前）

所有修订均基于开发集观察，在冻结与测试集运行之前作出，并记录原因。测试集冻结后不再修订。

| 编号 | 日期 | 修订 | 原因（开发集观察） |
|---|---|---|---|
| A1 | 2026-10-13 | **L2 定义细化**：主口径 L2 = L1 + 两条查询所引用的列上不违反 SpotIt+ 挖掘约束（记为 L2）；"全表所有列都满足"作为补充口径 L2-all 报告。 | SpotIt+ 自己的反例在 L2-all 下 0/144 通过、在 L2 下 61/143 通过：其约束只作用于与查询相关的列，L2-all 对所有方法都过严，无法区分方法。 |
| A2 | 2026-10-13 | **ParSEval 两个变体**：(a) `parseval`：官方 `disprove`，`set_semantics=True`（与主契约 C_set 一致），每对硬墙钟 10 s；(b) `parseval_l1`：同一生成器，但每个生成的数据库都交共享认证器，只接受 L1/C_set 见证，且在 10 s 内换随机种子重启——对 ParSEval 最有利的同预算版本。主比较使用 (b)。 | 官方 `disprove` 先检查空库并据此停止，空库见证不满足 L1（被引用表非空）；不改其生成器、只换接受条件，最公平。 |
| A3 | 2026-10-13 | **CGX 与所有自研基线统一"认证器在环"接受**：搜索阶段只有通过共享认证器 L1/C_set 判定的数据库才被返回；最终仍由全新连接独立重认证。 | 保证各方法的"找到"与协议终点一致，避免因接受条件不同产生的不公平。 |
| A4 | 2026-10-13 | **SpotIt 两种口径**：作者自报（其仓库 `VeriEQL_results_val_cc_null` 中经其验证与交叉检查的 incorrect）为主比较对象；本认证器复核（原始 SQL、原始 DDL）为补充。SpotIt+ 无交叉检查发布，作者自报 = 任一 bound 判为不等价。 | 开发集发现 SpotIt 把字符串字面量统一大写、不建模 NOT NULL/UNIQUE，导致 434 个自报中仅 190 个可在原始语义下复现；为避免被指"故意压低对手"，主比较仍用对其最有利的自报数。 |
| A5 | 2026-10-13 | **预算**：维持每对 10 s（开发集 v1 中 99% 的见证在 0.63 s 内找到，最长 2.4 s，10 s 已饱和）；消融在测试集的分层随机子样本（1,500 个不同对）上运行，主方法与基线在全部测试对上运行。 | 2 核机器上 8 个配置全量运行约需 35 小时以上。 |
| A6 | 2026-10-13 | **完全相同文本的对**（仅空白/结尾分号不同）对所有方法直接判为"无见证"并计入分母。 | 相同 SQL 文本在任何数据库上结果相同，这是可靠的、对所有方法一致的短路。 |
| A7 | 2026-10-13 | **新增 L1f（格式忠实）并设为主终点**：L1f = L1 + 文本列取值符合官方库观测到的词形（来源：SpotIt+ 作者公开的、从官方 BIRD 库挖掘的分类取值样本，123 列）+ 名字为日期/时间且无样本的文本列须为 ISO 风格。L2 改为在 L1f 之上叠加 SpotIt+ 约束（查询引用列）。所有方法（含基线）在生成/接受时都可使用同样的格式知识。 | 开发集 v1 的见证大量依赖不现实的文本编码（如 `'1990'` 写入日期时间列），这类"差异"在真实数据中不存在。改为更严的主口径是保守方向的修订。 |
| A8 | 2026-10-13 | **预算改为每个不同对 5 s（所有自运行方法相同）**；另在测试集 1,000 个不同对的随机子样本上，以 10 s 预算重跑 CGX 与 ParSEval-L1，作为预算敏感性检验。消融也在该子样本上（5 s）进行。 | 开发集中 CGX 99% 的见证在 0.63 s 内找到；全量 10 s 在 2 核机器上约需 27 小时，5 s 约 14 小时。各方法预算一致，公平性不受影响；SpotIt/SpotIt+ 仍使用其作者远大于此的预算。 |
| A9 | 2026-10-13 | **v4 方法改动（基于开发集"已知阳性"漏检）**：受控增长——一对多连接上的扇出复制（COUNT 与 COUNT DISTINCT、HAVING COUNT 阈值）、按 LIMIT/OFFSET 窗口构造足够多探针、字面量覆盖探针（每个等值字面量一个探针）、可比较字面量之间的插值值。 | 开发集 EX 判错（已知不等价）对上 v3 召回 94.3%，漏检的 60 对中大多属于以上结构。 |

| P1 | 2026-10-14 | **事后层级 L1n**：L1f + 查询引用列中，在官方 BIRD 库里从不为 NULL 的列，见证中也不得为 NULL（可空性由用户提供的官方库直接统计，798 列中 420 列从不为 NULL）。**O1f / O1n**：用官方库全量列格式画像（而非 SpotIt+ 公布的 123 列样本）重新认证。 | 中期结果显示约 43% 的 CGX 见证依赖真实数据中从未出现的 NULL；需如实量化。 |
| P2 | 2026-10-14 | **随机模糊基线的接受条件补正**：冻结版模糊基线返回的是"第一个结果不同的数据库"，未像 CGX/ParSEval-L1 那样"认证器在环"按 L1f 接受，与 A3 的表述不一致，对模糊基线不利。补救：对冻结版"找到但未通过 L1f"的对，用同一随机种子、认证器在环（L1f）重跑。对"未找到"的对，轨迹完全相同，无需重跑。论文报告补正后的数字，并在正文说明这一偏差。 | 公平性：不能让基线因实现疏漏吃亏。 |
| P3 | 2026-10-14 | **可空性感知版本（探索性）**：CGX-v5（生成与接受都避开"官方从不为 NULL"的引用列）、Fuzz-v5（同样的信息与 L1n 接受）、ParSEval-L1n（同一生成器，接受条件加 L1n）。三者使用完全相同的可空性知识，在全部 6,456 个不同 EX 判对对上以 5 s 预算运行。 | 回答"在 L1n 口径下，方法优势是否仍然成立"；三方信息对等，避免只给自己的方法加料。 |
| P3-更正 | 2026-10-14 | **P3 取消**：可空性感知版本被数据画像层级 R 取代（见 07 号文档），未运行。 | 避免重复消耗算力。 |
| Q1 | 2026-10-14 07:10 | **冻结队列在两步之间暂停**：CGX+SC 运行期间，对队列脚本所在 bash 进程发送 SIGSTOP。正在运行的 CGX+SC 不受影响，照常跑完；队列在它结束后不再启动下一步。剩余各步（已知阳性、ParSEval 官方版、消融、10 s 预算）稍后用 SIGCONT 恢复，运行时机器上不会有其他重负载任务。CGX+SC 运行期间只并发跑过最低优先级（nice 19）的小规模冒烟测试，CPU 份额约 1–2%。 | 让出算力用于 R 层方法在开发集上的调试，同时保证冻结版各步的墙钟预算不被并发任务挤占。 |
